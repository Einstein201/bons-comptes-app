# IF-13 — Tests du contrat des invitations

Cette livraison contient uniquement des tests HTTP pour UC04 et UC05. Elle
n'ajoute ni route, ni service métier, ni modèle Prisma, ni migration, ni frontend.

## Dépendances

IF-15 (UC03 et UC06) est encore en développement. Les données de préparation sont
donc créées directement avec Prisma : comptes fictifs, portefeuilles et adhésions
du créateur. Les tests ne passent ni par `POST /users`, ni par `POST /wallets`, ni
par une route de clôture.

Les JWT sont signés localement avec des secrets de test et le format d'IF-11.
Le vrai `JwtAuthGuard` et la vraie stratégie JWT restent actifs. Aucune route
d'invitation ou règle métier n'est simulée ; la persistance est vérifiée dans une
vraie base PostgreSQL locale.

## Exécution volontaire

Prérequis : dépendances backend installées et base PostgreSQL **locale dédiée**,
dont le nom commence par `if13_test`. Ne pas utiliser la base partagée Neon.
Depuis `backend/`, en remplaçant les identifiants fictifs ci-dessous :

```bash
export IF13_TEST_DATABASE_URL='postgresql://test_user:test_password@127.0.0.1:5432/if13_test_invitations?schema=public'

npx prisma generate
DATABASE_URL="$IF13_TEST_DATABASE_URL" \
DATABASE_URL_UNPOOLED="$IF13_TEST_DATABASE_URL" \
  npx prisma migrate deploy

npx vitest run --config vitest.invitations.config.ts
```

La base doit déjà exister. La suite ne crée pas de base et n'applique pas de
migrations elle-même. Elle refuse de démarrer si `IF13_TEST_DATABASE_URL` est
absente, vise un hôte distant ou utilise un autre préfixe de nom de base.
Elle nettoie uniquement les utilisateurs et portefeuilles créés par chaque test.

La suite utilise une configuration dédiée : elle est volontairement en échec
tant que les routes IF-13 sont absentes. Elle n'est pas incluse dans `npm test`
ni dans `npm run test:e2e` et n'utilise aucun `skip` ou échec marqué comme réussi.
Quand IF-13 sera implémenté, il faudra inclure cette suite dans la CI avant de
valider la fonctionnalité. Les tests ne prouvent pas encore sa conformité.

## Conventions proposées pour le contrat HTTP

Le billet ne précise pas tous les détails de pagination. Cette suite propose :

- `GET /invitations?limit=20&cursor=...` ;
- une enveloppe `{ data: [...], nextCursor: string | null }` ;
- `nextCursor: null` lorsqu'il n'existe aucune page suivante, y compris lorsqu'une
  dernière page contient exactement `limit` résultats ;
- un curseur opaque : aucun encodage particulier n'est imposé par les tests ;
- un tri `invitedAt DESC, id DESC` ;
- une limite entière entre 1 et 100, 20 par défaut ; une limite invalide ou un
  curseur mal formé donne `400`.

Chaque élément de `data` contient exactement `id`, `invitedAt` et `wallet`.
Le portefeuille contient exactement `id`, `title`, `description` et `status`.
Ces conventions devront être coordonnées avec l'implémentation IF-13 et le futur
frontend. Les tests de création et d'acceptation n'imposent pas de forme de
réponse supplémentaire au billet, mais vérifient l'absence de secrets.

Pour une tentative d'usurpation d'identité via un champ `userId` ajouté à une
requête de liste ou d'acceptation, le rejet du champ ou son ignorance sont admis,
à condition que l'identité du JWT reste la seule utilisée. La création refuse
toutes les propriétés non prévues avec `400`, conformément au billet.

Le schéma comporte uniquement `INVITED` et `MEMBER`. Aucun statut `CANCELLED`
n'est inventé. Une invitation d'un portefeuille fermé reste `INVITED`, mais son
acceptation est refusée avec `409`, comme demandé par IF-13.

## Couverture

| Sujet                 | Vérifications                                                                                                                                     |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentification      | Les trois routes refusent l'absence de JWT, les jetons invalides, expirés et de type refresh.                                                     |
| Envoi                 | Créateur seul, compte existant, portefeuille ouvert, adhésion INVITED et date d'invitation initialisée.                                           |
| Erreurs d'envoi       | Validation, champs supplémentaires, auto-invitation, compte ou portefeuille absent, doublon INVITED ou MEMBER.                                    |
| Liste                 | Isolation par utilisateur, exclusion des membres, champs publics, liste vide et portefeuille clos.                                                |
| Pagination            | Défaut 20, maximum 100, ordre déterministe à date égale, pages sans doublon, dernière page pleine, curseur d'une invitation acceptée entre-temps. |
| Acceptation           | Destinataire seul, passage de la même adhésion à MEMBER, acceptedAt renseigné, disparition de la liste.                                           |
| Erreurs d'acceptation | Invitation absente, autre utilisateur, identité falsifiée, invitation déjà acceptée, portefeuille fermé après l'envoi.                            |
| Concurrence           | Double envoi, double acceptation et acceptation concurrente par un tiers.                                                                         |
| Confidentialité       | Champs de liste stricts et absence de mot de passe, hachage, jeton ou secret dans les réponses vérifiées.                                         |

Les requêtes concurrentes sont émises contre la vraie API et une vraie base :
elles peuvent détecter une course, sans prouver à elles seules tous les ordres
d'exécution possibles. Le scénario de clôture vérifie un portefeuille fermé
après l'invitation et avant l'acceptation ; il ne simule pas une future route UC10.
